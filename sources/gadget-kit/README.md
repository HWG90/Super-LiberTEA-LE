# Goose Gadget Kit

Steam build 26251122; game.dll 6AE0E5FF, helldivers2.exe 6AE0964A; Lua 5.1/CFFI and DBF-MCM. (Ported from 26088801 on 2026-10-29: game.dll code and data did not move; exe addresses and witnesses remapped. Evidence: Linux HD2 Mods builds/26251122/maps/gadget-kit.)

**Unlocks** contains local equipment access and category switches. **Gameplay** includes **Passive AI**, which toggles the local Player no aggro flag (bit 25), plus independent mission timer, health, loaded-ammunition and reserve-ammunition holds. These controls default off and require local host ownership. Health holds do not prevent instant death or limb damage. Empty weapons need reloading before loaded rounds can be held. Switching off releases owned changes without writing stale values into recycled records.

**First Person** contains Native ADS / True First Person. F11 toggles first person; F8 opens the arms/weapon placement editor. Shift+F8 edits the head camera. **Bob and Sway** adjusts weapon and camera movement. Keys are configurable. Equip a firearm and return to normal on-foot gameplay before enabling. Full native ADS, Photo Mode ownership, weapon swaps and cleanup retain their existing guards. First person works independently of the Unlocks master switch.

This integrates the Windows Native ADS Camera Test 0.1.49 source into the kit's single MCM registration and lifecycle. Placement settings are stored under `first_person`; menu preferences use `first_person_` keys. Existing equipment/gameplay preferences are preserved. Native policy binaries use unique names derived from source hashes and remain resident until game exit.

Validation: all five cross-compiled native helpers pass their fixtures (198 cases plus alignment lifecycle checks); all 23 migrated upstream Lua suites pass with real CFFI under Lua 5.1. Shared-menu/settings/cleanup integration and existing kit tests pass. Live read-only validation passed for camera/player/weapon ownership, pose, FOV, blur, head camera, animation and renderer contracts. A bounded live activation entered native camera 6, applied pose/FOV/head/DoF policies and restored the native camera successfully. Visual placement acceptance remains user-dependent.

Build helpers with `python3 tools/build_first_person.py`. Run Lua fixtures with `python3 tools/test_first_person.py`; run integration with `lua5.1 tests/first_person_integration.lua`. Package the explicit payload allowlist with `python3 tools/package.py`. Native builders and migration tools document this workstation's evidence/toolchain paths. Packages exclude tests, logs, captured game data and private research.

Gameplay hold performance: protected scalar reads, roster checks, hash probes,
and exact game-module validation use the bundled read-only guarded_reads helper.
It uses ReadProcessMemory and retains the Lua reader as a fallback. Identical
byte reads may be reused within one synchronous freeze update; writes and native
health notifications discard that snapshot. No data survives into the next frame.
Catalogue audits check one entry every 62.5 ms instead of four every 250 ms.
Build and validate the helper with `python3 tools/build_memory.py`.

Hotkey compatibility: current MCM uses LLL's shared input service instead of the legacy camera_input export. The kit reads idle F11/F8 keys through the engine keyboard and acquires a separate token only while the placement editor is open. Focus, menu conflicts and held-key suppression are retained.

Unlock persistence: while Unlocks Enabled remains on, the kit repairs its own unlock overrides after in-place catalogue refreshes, also watches rows that were already unlocked at startup, and reacquires the catalogue after session/world reloads. Saved MCM Enabled and category settings restore on mod/game startup. This maintains local equipment access while the kit runs; it does not grant permanent account ownership. Turning Enabled off still restores owned overrides. Regression: `lua5.1 tests/unlock_persistence.lua`.

Remembered equipment (0.5.3): the kit now saves the last stable primary, sidearm, grenade, helmet, cape and armor IDs in the loader-owned `last_equipment` configuration. After a restart it waits for local-host unlocks and a stable ship profile, then restores those selections through the native player appearance/profile route without opening the Armory. Startup defaults never replace a pending saved loadout. Selection changes are saved after 1.5 seconds of stable ship reads. Disabled unlock categories are not restored. Existing selections lost before installing this version cannot be recovered: reselect them once, then leave Unlocks Enabled on. This does not persist mission stratagem selections, weapon attachments or arbitrary carried pickups.

Validation: saved-selection restart/readiness fixtures pass. Live native cape-change roundtrip passed and restored all six original selection IDs; no test loadout was retained. A full user-driven game restart remains the final acceptance check.

Timer guard fix (0.5.4): gameplay features now validate their own manager witnesses independently, accepting any verified equivalent reference. Cold/encrypted code for another feature no longer blocks the timer. Timer state, mission ownership, director relationship and countdown bounds remain guarded.

Startup restoration (0.5.5): unopened Armory code can remain packed even after the ship avatar exists. Startup restoration no longer fingerprints or calls that entry point. It restores the three weapon profile IDs and dirty marker directly and applies armor through the player appearance commit used during ship initialization. An already-open Armory still uses its own synchronized candidate/commit path. Regression: `luajit tests/equipment_startup.lua` simulates the Armory entry point being unavailable. Instant Extraction (0.5.6): Gameplay has an off-by-default `Instant Extraction` toggle. While local host in a mission, it shortens the native Extract (152) arrival timer to 0.1 seconds, once per extraction record. Native state transitions, flight and landing proceed normally. It does not target ordinary stratagem timers or mission time. Host/world ownership, code witnesses, component bounds, live descriptors and row identity are checked before the write. Unit and menu integration tests pass; live countdown completion is not yet verified.

Spawner (0.5.7): a **Spawner** MCM page equips a chosen support weapon into your hands during a mission: it replaces the current support weapon, applies the weapon's default attachments (the game's own default builder, e.g. the LAS-44 Nova's scope), selects it, and adds the matching backpack for two-part weapons. Off by default; local host, solo mission, normal on-foot gameplay, MCM and chat closed. The request path is Bridge Combat's `support_weapons.lua`, vendored under `src/spawner/` with only a scene option (4 = mission), its own request journal and kit wording; its 36 code guards, fingerprinted native calls and no-replay journal are unchanged. The 38-row catalogue (`src/spawner/catalogue.lua`) is generated from the live armory by `python3 -I tools/generate_spawner_catalogue.py`: Bridge Combat's 33 rows (all still valid on 6AD7C05D), the LAS-44 Nova and four live support items not yet named (listed by item id); each row has an authored pickup definition and a loadout package. Stratagem call-ins are not included yet. The kit's observer adds one mission fallback: the ship-only loadout-definition row Bridge Combat's backend requires is absent in missions, so the view is rebuilt from the player manager row with the same descriptor checks. Read-only live checks in a solo mission: the observer accepts the actor (state 4, context 2), and all 36 code guards and 12 native fingerprints match. Regression: `luajit tests/spawner.lua`. The Pickup component count owner guard (game 0x4D4190) covers ground-pickup zones, which inventory delivery never uses; it is checked once readable and may stay packed after a restart (seen 2026-10-25: 47/48 guards readable). Live delivery accepted 2026-10-25: LAS-44 Nova equipped directly in a solo mission with 1 default attachment (its scope). Code changes apply with `LiveLuaLoader.reload('live/goose_temporary_unlocks')`; no game restart is needed.

Fifth stratagem (0.5.8): the Spawner page's **Fifth stratagem** list and **Add to mission** append one stratagem to your mission stratagem list, once per mission, called with its normal code. 57 stratagems (`src/spawner/stratagems.lua`, `python3 -I tools/generate_spawner_stratagems.py`): the 27 orbital and eagle strikes, and the 30 support-weapon stratagems whose id is a Spawner catalogue item; a support weapon's package (and paired backpack) is made resident through the support path first, because the game otherwise fetches its animations, gets null and crashes (exe 0x55CC2E, traced 2026-10-25). The list is never shortened and existing entries never change (a lower count leaves a stale HUD card; a changed kind inherits the slot's cooldown). Solo mission only. Turrets, mines, vehicles and backpacks without a catalogue item are not listed yet. Regression: `luajit tests/spawner.lua`. Live acceptance 2026-10-25: RS-422 Railgun preloaded, added as the fifth stratagem, called in and picked up without a crash.

Complete all objectives (0.5.9): the **Gameplay** page has a **Complete all objectives** button. As local host in a mission it completes every unfinished objective, side objectives and undiscovered ones included, through the game's own completion step (game 0x5E1720, the routine about 170 objective types call when they finish): progress goes to its target, the objective is marked completed and discovered for every player, and the game then plays its normal completion handling. Objectives already completed or failed are left alone, and so is any objective the host does not own. The button queues one request; the next update checks the host session, the mission, the ObjectiveComponent manager bounds, each objective's map row and seven code witnesses, then completes them. The status line shows how many objectives are complete. Regression: `luajit tests/objectives.lua`. Read-only live check 2026-11-01 in a hosted bot mission: 7 objectives, every witness readable and matching, host authority on all rows.

Near clip (0.5.10): the **First Person** page has **Near clip distance (cm)** (default 15; 5 is the game's own distance, which turns it off) and **Near clip while aiming** (default off). In first person, anything closer to the camera than that distance is not drawn, so armor edges and gear sitting at the lens stop covering the view. The game sets the gameplay camera's near distance to 0.05 m on every camera update (game.dll 0x110DCAB, through the Camera API near setter at slot +0x68, from the .rdata constant at 0x2245EEC), so a Lua `Camera.set_near_range` is overwritten before the frame renders (measured live: 174 of 180 frames reset, no visible clip). A separate native helper (`native/near_clip`, `native_ads_near_26251122_*.dll`) swaps only that slot while first person runs and substitutes the configured distance for that one call, for the owned camera, while the first-person camera request (kind 6) is current and full ADS is released. Normal aim uses the aim value, which is the game's distance unless the toggle is on. Every other caller and camera passes through unchanged; a replaced camera or retired avatar row disarms it; End restores only its own pointer. It makes no executable writes or protection changes, and the game writes its own value again on the next update after End. Build and fixture: `python3 native/near_clip/build_near.py` (13 cases under wine); Lua: `tests/first_person/near_clip.lua`. Live check 2026-10-31: with that call muted, a 4 m near distance removed the gun and nearby ground from captured frames. The trial itself awaits in-game acceptance.
